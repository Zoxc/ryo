# Platforms: ELF and PE

Targets: `x86_64-unknown-linux-gnu` and `x86_64-pc-windows-msvc`.

| Concern | ELF (linux-gnu) | PE/COFF (windows-msvc) |
|---|---|---|
| Image registry | Registry object generated at final link, constructor in `.init_array` | Same object, constructor in `.CRT$XCU` (read-only, like the CRT's own `.CRT$XC*` sections), which the CRT runs before `main` or on `DLL_PROCESS_ATTACH` |
| Image sections | `.data.rel.ro.ryo_image`, `.data.ryo_image` | `.rdata$ryo_image`, `.data$ryo_image` (the loader applies base relocations to `.rdata` too). The constructor is in `.text$ryo_registry` |
| Image pointers to functions/statics in another shared object | Plain absolute relocation in the symbol table (the dynamic linker resolves it) | Functions and data: for every symbol from an upstream crate or an FFI library (the backend's test: `should_codegen_locally` is false for the target) that is used as an address (the `sym` of `addr.sym*` and `call.ext*`), the symbol slot holds the address of `__imp_<sym>` and is flagged indirect. Whether the target will end up in another DLL isn't known when compiling an rlib, so the rule applies always; when the definition is linked statically, `__imp_` still resolves: rustc defines `__imp_<sym>` for the data symbols of rlibs (`create_msvc_imps`, `rustc_codegen_llvm/src/back/write.rs:1312`), and for functions link.exe/lld-link synthesize it (warnings LNK4217 and LNK4286, which `rustc-ryo` silences with `/IGNORE` on msvc targets). The VM loads through the slot (`addr.sym.ind`, and the indirect form of the `call.ext` symbol load). So slots hold the real address, never an import thunk, and portal addresses compare equal to the defining image's portal for `vm::lookup_addr` and fn-pointer equality. Island symbols (the `island` instructions' and the calls' `island` operand) are always direct: they are only called, and a direct reference to a function in another DLL resolves to its import thunk. That holds because islands are functions and rustc exports functions without `DATA` (`rustc_codegen_ssa/src/back/link.rs:2603-2611`); the thunk's address isn't comparable with the real one, which islands never need. Slots are keyed by name and flags, so an upstream function used both ways gets a direct and an indirect slot. Every function with an indirect slot also gets a direct one: lld synthesizes `__imp_<sym>` only for symbols that are already defined, so without a direct reference the archive member defining a statically linked function would never be extracted; for a function in a DLL the direct slot resolves to its import thunk, unused. The same holds for foreign statics from a static library (a C library has no `__imp_` of its own), which get a direct slot too; upstream Rust statics don't need one (rustc defines their `__imp_`), and statics in a DLL can't have one (data has no thunk). `tests/vm_ffi` covers the static case, but rust-lld links it even without the direct slot (it resolves `__imp_` of that archive member's data symbol), unlike the function case in `collections`; the slot is kept for linkers that don't. The image writer checks that each `sym` operand's slot matches its instruction, and that portals and allocation relocations never use indirect slots. Constants pointing at such data go into the image's writable `fixups` area and are patched once at registration |
| Registry constructor calling `ryo_vm_register` | Direct call (PLT if `ryo_rt` is in a shared object) | Tail jump through `__imp_ryo_vm_register` when `ryo_rt` is in another DLL (its linkage for the output's crate type is `Dynamic` or `IncludedFromDylib`), a direct `jmp` otherwise. It moves no stack pointer, so it needs no unwind info |
| Data relocations | `R_X86_64_64` | `IMAGE_REL_AMD64_ADDR64`; `IMAGE_REL_AMD64_REL32` in the constructor. No `ADDR32NB` (RVAs) is needed: the objects have no `.pdata` |
| Portal symbols exported from a Rust dylib | Visibility from the exported-symbols queries | `dllexport` and the export list rustc generates from the exported-symbols queries. Portals appear there under the original symbol name. Image and registry symbols are external but never in the export list, so they stay inside the link unit |
| VM stack | `mmap` + `mprotect` guard page | `VirtualAlloc` (committed, so it counts against the commit limit, but pages only get memory when touched) + a `PAGE_NOACCESS` guard page (not `PAGE_GUARD`, which only traps once), via `#[link(name = "kernel32")]` |
| Thread exit | pthread key destructor | FLS callback. A DLL containing `ryo_rt` must not be unloaded (images are never unregistered anyway): the callback would dangle |
| TLS for VM state | `#[thread_local]` (initial-exec in exe, general-dynamic in dylib) | `#[thread_local]` (implicit TLS `.tls`, in exe and DLL) |
| Panics out of islands | Itanium unwinding, caught by `catch_unwind` in `ryo_rt` | SEH-based Rust panics, same `catch_unwind`. The VM never unwinds natively, so only the Rust-compiled handlers need unwind info, and rustc emits it |
| Runtime | `libryo_rt.rlib` in the sysroot, linked as a Rust crate | Same, so the linker flavor (`ld`/`lld`/`link.exe`) doesn't matter |
| ABI | SysV | Win64: different indirect/`i128`/aggregate rules. The ABI sweep test runs on both |
| Build entry point | `y.sh` | `y.cmd` / `y.ps1`. `y test` builds the C programs with `cl` (from a Visual Studio developer environment). `.github/workflows/ci.yml` is set up to run `y build` and `y test` on Linux and Windows; it has not run yet (see Status) |
| Cross-checking | | `y build --target x86_64-pc-windows-msvc` (on any host with that rust-std installed) adds std and `ryo_rt` for it to `dist/`, so `rustc-ryo --target x86_64-pc-windows-msvc` can build rlibs and objects there. `y test --cross x86_64-pc-windows-msvc` then builds the corpus with plain rustc and `rustc-ryo` and links it with the sysroot's `rust-lld` against empty stand-in import libraries (`/force:unresolved`); it fails if the ryo build leaves a symbol unresolved that plain rustc's doesn't, other than the listed CRT/SDK imports of `ryo_rt`. Nothing runs |

**Status**: the PE column is implemented and cross-checked from Linux only (`y test --cross
x86_64-pc-windows-msvc`: objects, sections, relocations and an lld-link link against stand-in
import libraries). Nothing has run on Windows yet. It counts as unverified until the Windows
job of `.github/workflows/ci.yml` (`y build`, `y test` on windows-latest) has passed.

The backend's format-specific parts sit behind one `trait ObjectFormat`, covering the image
section, symbol and relocation kinds, the registry constructor section and import
indirection. `object::BinaryFormat` picks the implementation from the target spec.
