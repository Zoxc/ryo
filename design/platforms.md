# Platforms: ELF, PE and Mach-O

Targets: `x86_64-unknown-linux-gnu`, `x86_64-pc-windows-msvc` and `x86_64-apple-darwin`
(Mach-O, [below](#mach-o-x86_64-apple-darwin); arm64 Macs run it under Rosetta).

| Concern | ELF (linux-gnu) | PE/COFF (windows-msvc) |
|---|---|---|
| Image registry | Each image object's entry in `ryo_images` (`SHF_GNU_RETAIN`); a registry stub generated at final link walks `__start_ryo_images`..`__stop_ryo_images` (hidden references), constructor in `.init_array.00000`, so it runs before every other constructor (std's own, in `.init_array.00099`, may be VM code) | Entries in `.ryo$m`, between the stub's markers in `.ryo$a` and `.ryo$z` (grouped sections sort by suffix; null entries, as incremental-link padding, are skipped), constructor in `.CRT$XCT` (read-only, like the CRT's own `.CRT$XC*` sections), which the CRT runs before `main` or on `DLL_PROCESS_ATTACH`, and before the user initializers in `.CRT$XCU` (std's among them) |
| Image sections | `.data.rel.ro.ryo_image`, `.data.ryo_image`, the code in `.text.ryo_image` | `.rdata$ryo_image`, `.data$ryo_image` (the loader applies base relocations to `.rdata` too), the code in `.text$ryo_image`. The constructor is in `.text$ryo_registry` |
| Unwind info of VM code | `.eh_frame` (one CIE with `rust_eh_personality`, read through an image symbol slot; one FDE per function) and LSDAs in `.gcc_except_table.ryo_image`, so panics run VM landing pads ([vm.md](vm.md#unwinding)) | `.pdata`/`.xdata` per function, describing the prologue (`push rbp; mov rbp, rsp; sub rsp, F`) with `rbp` as the frame register (offset 0) (VM code always keeps the frame pointer on PE, [vm.md](vm.md#frames)), and naming `ryo_rt`'s `ryo_seh_handler` (an `IMAGE_REL_AMD64_ADDR32NB` to its symbol) with the function's LSDA as its handler data. The handler calls the landing pads during the native unwind, on its stack, through a trampoline; they are in a pad region after the body, with an entry of its own (`sub rsp, 40`, no frame register), where `resume` returns ([vm.md](vm.md#pe-seh)). Terminate pads catch C++ exceptions in the search phase with `RtlUnwindEx` (a kernel32 import of `ryo_rt`) |
| Island calls from VM code | `rdi` = `fp`, `rsi` = `ops` (the Rust ABI) | `rcx`, `rdx`, and the 32 bytes of shadow space at the frame's bottom (in the pad region, the shadow space its entry allocated). Handlers take the platform's C convention: `sysv64` on ELF, Win64 on PE (`rcx, rdx, r8, r9`, a fifth argument past the shadow space, `fp` from `rbp`, [vm.md](vm.md#handlers)) |
| Image pointers to functions/statics in another shared object | Plain absolute relocation in the symbol table (the dynamic linker resolves it) | Functions and data: for every symbol from an upstream crate or an FFI library (the backend's test: `should_codegen_locally` is false for the target) that is used as an address (the `sym` of `addr.sym*` and `call.sym*`), the symbol slot holds the address of `__imp_<sym>` and is flagged indirect. Whether the target will end up in another DLL isn't known when compiling an rlib, so the rule applies always; when the definition is linked statically, `__imp_` still resolves: rustc defines `__imp_<sym>` for the data symbols of rlibs (`create_msvc_imps`, `rustc_codegen_llvm/src/back/write.rs:1312`), and for functions link.exe/lld-link synthesize it (warnings LNK4217 and LNK4286, which `rustc-ryo` silences with `/IGNORE` on msvc targets). The VM loads through the slot (`addr.sym.ind`, and `call.sym.ind`: `mov rax, [rip + slot]; call [rax]`). So slots hold the real address, never an import thunk, and fn pointers to a function compare equal however they were obtained. Island symbols (the `island` instructions' `isl` operand) are always direct: they are only called, and a direct reference to a function in another DLL resolves to its import thunk. That holds because islands are functions and rustc exports functions without `DATA` (`rustc_codegen_ssa/src/back/link.rs:2603-2611`); the thunk's address isn't comparable with the real one, which islands never need. Slots are keyed by name and flags, so an upstream function used both ways gets a direct and an indirect slot. Every function with an indirect slot also gets a direct one: lld synthesizes `__imp_<sym>` only for symbols that are already defined, so without a direct reference the archive member defining a statically linked function would never be extracted; for a function in a DLL the direct slot resolves to its import thunk, unused. The same holds for foreign statics from a static library (a C library has no `__imp_` of its own), which get a direct slot too; upstream Rust statics don't need one (rustc defines their `__imp_`), and statics in a DLL can't have one (data has no thunk). `tests/vm_ffi` covers the static case, but rust-lld links it even without the direct slot (it resolves `__imp_` of that archive member's data symbol), unlike the function case in `collections`; the slot is kept for linkers that don't. The image writer checks that each `sym` operand's slot matches its instruction, and that allocation relocations never use indirect slots. Constants pointing at such data go into the image's writable `fixups` area and are patched once at registration |
| Registry constructor calling `ryo_vm_register` | Direct call (PLT if `ryo_rt` is in a shared object) | Tail jump through `__imp_ryo_vm_register` when `ryo_rt` is in another DLL (its linkage for the output's crate type is `Dynamic` or `IncludedFromDylib`), a direct `jmp` otherwise. It moves no stack pointer, so it needs no unwind info |
| Relocations | `R_X86_64_64` (data), `R_X86_64_PC32` (RIP-relative code fields, `.eh_frame`), `R_X86_64_PLT32` (calls of the handlers and `ryo_probe_stack`) | `IMAGE_REL_AMD64_ADDR64` (data), `IMAGE_REL_AMD64_REL32` (code fields and calls, the constructor), `IMAGE_REL_AMD64_ADDR32NB` (`.pdata`) |
| VM function symbols exported from a Rust dylib | Visibility from the exported-symbols queries, which the image's global symbols follow | `dllexport` and the export list rustc generates from the exported-symbols queries (PE symbols have no visibility, and weak VM functions get ordinary definitions, `objfile.rs`, `global_function`). Image and registry symbols are external but never in the export list, so they stay inside the link unit |
| VM frames | On the native thread stack: no VM stack, and nothing to free at thread exit. Frames of 4096 bytes or more probe the stack (`ryo_probe_stack`), so overflow hits the guard page | Same. The prologue saves only `rbp`: the Win64 handlers preserve `rdi`, `rsi` and `xmm6`–`xmm15`, as VM code must for its callers, and inline sequences don't use `rdi` and `rsi`; every frame reserves its calls' 32 bytes of shadow space at its bottom ([vm.md](vm.md#frames)). No red zone: LLVM gives `sysv64` functions one by their convention even on Windows, where exception dispatch, APCs and debuggers may write below `rsp`, so `ryo_rt` and the sealed JIT are built with `-Cno-redzone=yes` (`y build`), and `y test --cross` fails if any of their code accesses memory below `rsp` |
| Panics out of islands | Itanium unwinding through the VM frames, with their landing pads | SEH-based Rust panics (and foreign C++ exceptions, and SEH ones), unwinding through the VM frames, whose landing pads run in the same unwind ([vm.md](vm.md#pe-seh)). `RUST_BACKTRACE` walks through them too, but names a VM function with internal linkage after the nearest external symbol before it: dbghelp finds only the PDB's public (external) symbols, and VM code has no CodeView records |
| Runtime | `libryo_rt.rlib` in the sysroot, linked as a Rust crate, with the sealed JIT bundled ([jit.md](jit.md#packaging): its globals but `ryo_jit_start` made local) | Same, so the linker flavor (`ld`/`lld`/`link.exe`) doesn't matter. The bundled JIT is sealed by renaming its few external definitions (`__ryo_jit$<name>`); the JIT's SSA tier and re-encoding pipeline both take PE code (the SSA tier treats `rdi`/`rsi` as callee-saved there, [jit.md](jit.md#back-end)), and it registers its code's unwind info with `RtlAddFunctionTable`, with the handler as for AOT code, through a thunk in its code memory ([jit.md](jit.md#unwinding-and-profiling)); it has not run on Windows yet. The trips save `rdi`, `rsi` and `xmm6`–`xmm15` around their `sysv64` Rust code and wait with `WaitOnAddress` |
| ABI of VM functions | SysV: `rdi`…`r9`, `xmm0`–`xmm7`, `i128` in two GPRs or on the stack ([vm.md](vm.md#calls-and-islands)) | Win64: four positional registers, 32 bytes of shadow space; an `i128` takes two positions, an `f16` the low bytes of an `xmm` or slot, an `f128` goes by reference and returns by sret (in a `Pair` it keeps the function native) ([vm.md](vm.md#calls-and-islands)). The ABI sweep test (`tests/vm_abi.rs`) runs on both |
| Build entry point | `y.sh` | `y.cmd` / `y.ps1`. `y test` builds the C programs with `cl`: from `PATH` in a Visual Studio developer environment, else from the newest Visual Studio with the x64 C++ tools that `vswhere` finds, with the environment its `vcvars64.bat` sets up. Nothing else needs a developer environment (rustc finds `link.exe` itself; the archive and object tools are the toolchain's `llvm-tools`). `.github/workflows/ci.yml` is set up to run `y build` and `y test` on Linux, Windows and x86_64 macOS (an Intel runner, which also runs `y test` with the JIT from the first call and by OSR); its Windows and macOS jobs have not passed yet (see Status, and [Mach-O](#mach-o-x86_64-apple-darwin)) |
| Cross-checking | | `y build --target x86_64-pc-windows-msvc` (on any host with that rust-std installed) adds std and `ryo_rt` for it to `dist/`, so `rustc-ryo --target x86_64-pc-windows-msvc` can build rlibs and objects there. `y test --cross x86_64-pc-windows-msvc` then builds the corpus with plain rustc and `rustc-ryo` and links it with the sysroot's `rust-lld` against empty stand-in import libraries (`/force:unresolved`); it fails if the ryo build leaves a symbol unresolved that plain rustc's doesn't, other than the listed CRT/SDK imports of `ryo_rt`, and that the functions each program lists are bytecode. It also checks the unwind tables of each linked output (`llvm-readobj --unwind` with lld's `/lldmap`): every instruction of the VM images and of `ryo_rt` that moves `rsp` is in a `RUNTIME_FUNCTION`, each entry's unwind codes are those of its prologue, and VM epilogues free the prologue's allocation; that `ryo_rt` keeps to core (`rt-core-only`) and has no red zone; and that LLVM still places the Rust ABI's `i128` as `lower/sig.rs` assumes (`win64-i128`: two positions, returned in `rax:rdx`). It fails without `rust-lld`. Nothing runs |

**Status**: the PE column is implemented and cross-checked from Linux only (`y test --cross
x86_64-pc-windows-msvc`: objects, sections, relocations and an lld-link link against stand-in
import libraries). The first Windows CI run built everything, and its failures were
expectations of the tests rather than of the PE column (CRLF checkouts, the Win64 native
cases, the landing pads, since run by `ryo_seh_handler`, and the backtrace names above). It
counts as unverified until the Windows job of `.github/workflows/ci.yml` (`y build`, `y test`
on windows-latest) has passed; the SEH unwinding in particular has never run.

## Mach-O (x86_64-apple-darwin)

macOS uses the ELF column's mechanisms (SysV ABI, Itanium unwinding with landing pads, no
indirect slots: dyld binds data pointers to symbols in other dylibs, and the TLS shims are
the backend's, as `dll_tls_export` holds), in Mach-O objects (`objfile.rs`, `MachO`). arm64
is out of scope.

| Concern | Mach-O |
|---|---|
| Symbols | rustc's names with the `_` prefix (`ObjectFormat::mangle`; the `object` crate's own mangling is off, as it skips symbols of unknown kind), Hidden is `N_PEXT`, weak `N_WEAK_DEF`, protected is exported as default. `LC_BUILD_VERSION` with the session's deployment target (`MACOSX_DEPLOYMENT_TARGET`, `Session::apple_deployment_target`), as rustc's own objects have it. The objects don't set `MH_SUBSECTIONS_VIA_SYMBOLS`: calls between image functions have no relocations, so each section stays one atom |
| Image sections | `__DATA,__const` (read-only part; ld64 moves it to `__DATA_CONST`), `__DATA,__data`, the code in `__TEXT,__text`, the anchor and `__ryo_main` slots in `__DATA,__ryo_anchor` and `__DATA,__ryo_main` (one object can't have two sections of one name), the registration entry in `__DATA,__ryo_images` (`S_ATTR_NO_DEAD_STRIP`) |
| Unwind info of VM code | `__TEXT,__eh_frame` (`S_COALESCED`, no-TOC, strip-static-syms, live-support, as LLVM's) and `__TEXT,__gcc_except_tab`, in the form LLVM writes, which is what ld64, ld-prime and lld read: the CIE's personality is an `X86_64_RELOC_GOT` to `_rust_eh_personality` (the image's personality slot stays, unused by it), the FDE and LSDA pointers are 8 bytes (`DW_EH_PE_pcrel \| DW_EH_PE_absptr`, `EhPointers::Abs8`: lld reads 4-byte ones unsigned and loses FDEs whose code comes before them) and have no relocations: they hold the targets' addresses in the object (`patch_by_address`, after the object is written), from which the linker finds them. No `__compact_unwind`: the linker makes `__unwind_info` from the FDEs (lld keeps them as DWARF entries; ld64 may turn some into compact encodings) |
| Relocations | All extern: `object` writes implicit addends without the target section's address, which section-numbered ones need, so references to a section go to a linker-private local symbol at its start (`l__text`, …). `X86_64_RELOC_UNSIGNED` (data), `X86_64_RELOC_SIGNED` (RIP-relative code fields; an ELF addend of −4 is an implicit 0, and an immediate after the field needs no `SIGNED_1` with an extern target), `X86_64_RELOC_BRANCH` (handler and probe calls; ld64 adds a stub for a dylib `ryo_rt`), `X86_64_RELOC_GOT` (the personality). No subtractor pairs: nothing needs one |
| Image registry | The registry stub's constructor (as on ELF: `lea rdi`, `lea rsi` of `section$start$__DATA$__ryo_images` and `section$end$...`, `jmp _ryo_vm_register`) in `__DATA,__mod_init_func` (`S_MOD_INIT_FUNC_POINTERS`). Mach-O has no constructor priorities: ld64 and lld lay out `__mod_init_func` in input order, and dyld runs an image's initializers in that order (after those of the dylibs it depends on). So `link` puts the registry object first among the output's objects, ahead of the crate's own objects and every rlib, and the registry runs before any user constructor of the link unit (`tests/vm_sysroot.rs`'s, which enters the VM). `y test --cross x86_64-apple-darwin` checks (`registry-first`) that with lld the registry constructor is the first entry. A constructor placed ahead of rustc's objects still runs first: one from `-Wl` arguments or another linked object, or a C program's when it links a ryo staticlib, whose image member comes before the registry member it pulls in. VM code it runs works unregistered: Mach-O images have no fixups, and the JIT's trips register the tripping record's image themselves ([vm.md](vm.md#image-format), `registry::ensure`), so only cross-image lookups (`image_at`) miss the link unit's other images until the constructor runs |
| Runtime, JIT | `y build --target x86_64-apple-darwin` builds std, `ryo_rt` and the sealed JIT (`_ryo_jit_start` its only external symbol, [jit.md](jit.md#packaging)). The JIT's OS layer (`vm/jit/src/sys/macos.rs`: one `__register_frame` per FDE; `vmem`'s hint-and-verify `mmap` and `mprotect`; `__ulock` waits in the trips) is enabled and has never run. A hardened-runtime binary needs the `com.apple.security.cs.allow-unsigned-executable-memory` entitlement |

**Status**: implemented and checked from Linux only: `objfile.rs`'s unit tests read the image
and registry objects back with `object` (sections, symbols, relocation types and implicit
addends, the `__eh_frame` layout and pointers); by hand, a program built with
`rustc-ryo --target x86_64-apple-darwin` linked with `rust-lld -flavor darwin` against
stand-in `.tbd` libraries (`-undefined dynamic_lookup`) gets a DWARF `__unwind_info` entry
with its LSDA for every VM function, the constructor in `__mod_init_func`, the registration
entries and `__ryo_main` pointing where they should (checked before the registry stub
replaced the list of image symbols; the stub is checked by the unit tests). Nothing has run on macOS, and neither ld64
nor ld-prime has linked it: the macOS job of `.github/workflows/ci.yml` (`y build`, `y test`, which
includes the `vm/` workspace's tests, the in-memory VM and JIT tests among them) has not passed
yet.

The backend's format-specific parts sit behind one `trait ObjectFormat`, covering the image
section, symbol and relocation kinds, the registry constructor section, import indirection,
symbol name mangling and Mach-O's relocation-free `__eh_frame`. `object::BinaryFormat` picks the implementation from the target spec.
